# Faculty Candidate Personal Website — Design Spec

**Date:** 2026-07-30
**Status:** Approved (pending final spec review)
**Owner:** Site author (postdoctoral researcher, Chemical Engineering faculty candidate)

## 1. Purpose

A single-page personal website for a postdoctoral researcher applying for
Chemical Engineering faculty positions in the US. It presents the author to
hiring committees: who they are, their training, their research, and their
publications. Publications stay current automatically via a scheduled sync from
the author's ORCID record.

Success criteria:

- A hiring committee member can, in under a minute, find the author's research
  focus, background, publications, and CV.
- Publications refresh automatically without the author editing the site.
- The author can update all prose content by editing one file and swapping two
  asset files (headshot, CV) — no toolchain required on their machine.
- Zero hosting cost; loads fast; works on mobile; no tracking.

## 2. Scope

### In scope (v1)

- Single-page scrolling site with sticky navigation.
- Sections: Hero, About, Research interests, Publications, Teaching,
  Awards/honors, Contact + links.
- Headshot photo in the hero.
- "Download CV" button linking to a PDF.
- Automatic publications list sourced from the ORCID public API, refreshed on a
  weekly schedule and on manual trigger, via GitHub Actions.
- Prominent link to the author's Google Scholar profile.
- Classic academic visual style with a deep-navy accent.
- Deployment to GitHub Pages with a custom domain.

### Out of scope (v1)

- Google Scholar scraping (unreliable; blocked by Google). Scholar is linked,
  not scraped.
- Citation-count enrichment per paper (possible later add-on).
- Multi-page site, blog, or news feed.
- Any server-side runtime or database.
- Local build tooling (no Node/Ruby required locally).

## 3. Technical approach

Plain hand-written static site: HTML, CSS, and vanilla JavaScript. No framework
and no local build step.

**Rationale.** For a single-page academic site, hand-written HTML/CSS is
simpler than a static-site generator, loads instantly, has no dependencies to
rot, and is trivial to edit. A generator (Eleventy, Astro) or an academic
template (e.g. al-folio) would add a Node or Ruby build dependency the author
would need to install and maintain — and Node is not installed on the author's
machine. The only automation, the ORCID publications sync, runs in the cloud in
GitHub Actions, so the author's machine never needs a toolchain.

## 4. Repository structure

```
/
├── index.html                       # the entire page
├── css/
│   └── style.css                    # all styles
├── js/
│   └── main.js                      # sticky-nav behavior; renders publications from JSON
├── data/
│   ├── content.yml                  # author-edited: about, education, research, teaching, awards, links, meta
│   └── publications.json            # auto-generated by the Action; not hand-edited
├── assets/
│   ├── headshot.jpg                 # author photo
│   └── cv.pdf                       # author CV
├── scripts/
│   └── sync_orcid.py                # fetches ORCID works -> writes data/publications.json
├── .github/
│   └── workflows/
│       └── update-publications.yml  # scheduled + manual sync workflow
├── CNAME                            # custom domain for GitHub Pages
├── README.md                        # how to edit content, add CV, run/trigger sync, deploy
└── docs/superpowers/specs/          # this spec and future specs
```

Content/data separation: the author edits only `data/content.yml` and the two
files in `assets/`. Everything in `data/publications.json` is machine-generated.

## 5. Page structure (single-page scroll)

Sticky top navigation bar showing the author's name on the left and jump links
(About, Research, Publications, Teaching, Awards, Contact) on the right. The nav
highlights the active section on scroll. Smooth-scroll to anchors.

Sections, in order:

1. **Hero.** Full name, current title and institution, a one-line research
   tagline, circular headshot, a "Download CV" button, and icon links to Google
   Scholar, ORCID, email, and any other profiles.
2. **About.** A few short paragraphs of prose (from `content.yml`).
3. **Research interests.** Three to four themes, each a short heading plus a
   one- or two-sentence blurb (from `content.yml`).
4. **Publications.** Auto-generated from ORCID. Newest first, grouped by year
   with year subheadings. Each entry shows title, author list (author's own name
   emphasized), venue, year, and a DOI link when available. A prominent "See all
   on Google Scholar" link sits at the top or bottom of the section.
5. **Teaching.** Teaching philosophy and a list of courses taught or proposed
   (from `content.yml`).
6. **Awards / honors.** A dated list (from `content.yml`).
7. **Contact + links.** Email and all profile links (Google Scholar, ORCID,
   LinkedIn, GitHub, etc.). Doubles as the footer.

## 6. Content model (`data/content.yml`)

A single YAML file the author edits. Indicative shape:

```yaml
meta:
  name: "Full Name"
  title: "Postdoctoral Researcher"
  institution: "Institution / Lab"
  tagline: "One-line research summary"
  email: "name@example.com"
  orcid_id: "0000-0000-0000-0000"     # drives the publications sync
  scholar_url: "https://scholar.google.com/citations?user=XXXX"
  links:                                # arbitrary labeled profile links
    - {label: "ORCID",   url: "https://orcid.org/0000-0000-0000-0000"}
    - {label: "LinkedIn", url: "https://linkedin.com/in/..."}
    - {label: "GitHub",  url: "https://github.com/..."}
about:
  - "Paragraph one."
  - "Paragraph two."
education:
  - {degree: "Ph.D., Chemical Engineering", institution: "University", year: "20XX"}
  - {degree: "B.S., Chemical Engineering",  institution: "University", year: "20XX"}
research_interests:
  - {heading: "Theme one", body: "Short blurb."}
  - {heading: "Theme two", body: "Short blurb."}
teaching:
  philosophy: "Short teaching-philosophy paragraph."
  courses:
    - "Course or proposed course one"
    - "Course or proposed course two"
awards:
  - {year: "20XX", description: "Award or honor"}
```

Because the site is static and does not run a build step, `content.yml` is read
at page load by `js/main.js`. Options considered: (a) parse YAML in the browser
with a small bundled parser included as a static asset, or (b) have the ORCID
GitHub Action also transpile `content.yml` to a `content.json` on each run. The
implementation plan will choose one; the author-facing contract (edit
`content.yml`) is unchanged either way. Default preference: browser-side parse
with a tiny bundled YAML parser, so a content edit needs no Action run to appear.

## 7. Publications auto-sync

Source: the **ORCID public API** (`https://pub.orcid.org/v3.0/{orcid_id}/works`),
which requires no authentication for public records and returns the author's
work summaries. ORCID is authoritative about which works belong to the author.

`scripts/sync_orcid.py`:

1. Reads the ORCID iD from `data/content.yml` (or an env var / workflow input).
2. Calls the ORCID public API with an `Accept: application/json` header.
3. Extracts per work: title, journal/venue, publication year, type, DOI (and a
   DOI URL), and contributor/author names when present.
4. De-duplicates, sorts newest-first, and writes `data/publications.json`.
5. On any network or parse failure, exits without overwriting the existing
   `data/publications.json`, so the live site keeps its last good list.

`.github/workflows/update-publications.yml`:

- Triggers: `schedule` (weekly cron), `workflow_dispatch` (manual button), and
  optionally `push` to main.
- Steps: checkout, set up Python, run `sync_orcid.py`, and if
  `data/publications.json` changed, commit and push it back to the repo. The push
  redeploys GitHub Pages.
- Uses the built-in `GITHUB_TOKEN`; no secrets required for a public ORCID
  record.

`js/main.js` fetches `data/publications.json` at page load and renders the
Publications section (grouped by year). The Google Scholar link is rendered from
`meta.scholar_url` and is never scraped.

Failure behavior is fail-safe: the page always renders whatever is in the
committed `publications.json`; a failed sync is a no-op, not a broken page.

## 8. Visual design

Classic academic style with a deep-navy accent.

- **Type.** A clean web serif for headings (e.g. Source Serif or Charter);
  sans-serif for body text for on-screen readability.
- **Color.** Deep navy (approximately `#1a2a4a`) for headings, links, active-nav
  underline, and the CV button. Off-white/near-white page background. Muted gray
  for secondary text and hairline dividers.
- **Layout.** Single readable content column (~720px max width) centered with
  generous margins. Circular headshot in the hero. Hairline dividers between
  sections. Fully responsive down to mobile; nav collapses gracefully on small
  screens.
- **Non-functional.** Fast (no framework payload), accessible (semantic
  headings, sufficient contrast, keyboard-navigable), and privacy-respecting (no
  analytics or third-party trackers).

## 9. Deployment

- GitHub repository with GitHub Pages enabled (deploy from the default branch).
- Custom domain configured via a `CNAME` file plus DNS records at the author's
  registrar. HTTPS certificate auto-provisioned by GitHub Pages.
- The publications Action commits back to the same branch, which triggers a
  redeploy.
- `README.md` documents: editing `content.yml`, replacing `headshot.jpg` and
  `cv.pdf`, manually triggering the sync, and the DNS/custom-domain steps.

## 10. Author-supplied content (placeholders shipped)

The site ships with clearly-marked placeholder content so it renders correctly
from day one. The author later supplies:

- ORCID iD (enables the live publications sync).
- About, Research interests, Teaching, and Awards text; education history.
- Email and profile URLs (Google Scholar, ORCID, and any others).
- `assets/headshot.jpg` and `assets/cv.pdf`.
- The custom domain name (for `CNAME` and DNS).

## 11. Open questions for implementation

- YAML handling: browser-side parse vs. Action-side transpile to JSON
  (Section 6). Default: browser-side parse.
- Exact web-serif choice and whether to self-host the font (privacy, offline)
  vs. load from a font CDN.
- Cron frequency (default weekly) and whether to also sync on push.
